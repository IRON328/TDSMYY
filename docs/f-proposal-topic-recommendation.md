## 一、产品定义

**做什么**：用户进入第 2 阶段「选题分析」时如果还没有方向，系统基于 **56 份优秀获奖题目**的结构化知识，给出 3 个候选选题，每个附可执行性判断、与参考题目的差异说明、以及做不下去的风险。

> **对外措辞纪律（用户明确要求）**：统一写「**优秀获奖题目中**」。
> **不写**届次（「2025 年」「第 N 届」）、**不写**层级（省赛/国赛）、**不写**奖项等级（省一/国二）。
>
> 理由不是回避，而是这三项对用户判断没帮助，反而会引入歧义：写「省赛」会被读成"含金量低"，
> 写「2025 年」会让系统显得过时。用户真正需要的是「这个方向已经有多少人做过、切口被占到哪里」，
> 这跟作品是哪一届、哪个层级无关。
>
> **但内部必须记**：语料是单批、非历年。这条内部事实用来守两件事——禁止趋势判断（§5.4）、
> 禁止与首页真题合并统计（§2.3）。

**不做什么**（边界比功能更重要）：

| 不做 | 原因 |
|---|---|
| 从零自由生成题目 | 无依据的生成等于让模型编，产出无法与获奖范式对齐 |
| 承诺「这个题能获奖」 | 获奖受学校资源、指导老师、答辩发挥影响，选题只是必要条件 |
| 替用户决定选题 | 只给候选与依据，采用权仍在用户，与第 2 阶段「用户选定方向」的既有设计一致 |
| 生成完整研究方案 | 那是第 3 阶段的事，越界会让两阶段职责混淆 |
| **做可浏览的选题库** | 范围已定（2026-10-27）：语料只作推荐依据。用户看到的是「针对你的方向给的 3 个候选」与「这个方向的路况」，**不是 56 道题的清单**。不建表、不做后台、不做题库前台 |

**这条边界带来一个必须补偿的代价**：用户无法自己浏览题库、自己判断。所以推荐结果必须自带
**可核查的依据**（§6.3），否则「凭什么信你」无从回答。

**一句话定位**：不是「AI 帮你写个题」，而是「**帮你找到一个你自己做得下来、且评审能看出差异的好题**」。

## 二、语料现状（已实测，2026-10-27）

语料位置：`D:\tipdmsmyy\2026市场调查大赛省赛作品`

| 项 | 实测结果 |
|---|---|
| 文件总数 | 111 |
| 报告 PDF | 56 份 |
| 答辩 PPT | 55 份 |
| 成对完整度 | 基本成对，56 报告对 55 PPT（有 1 份报告缺 PPT、1 份为附录单独成文件） |
| **是否文字版** | **56 / 56 全部为文字版，无扫描件** → 不需要 OCR |
| 平均页数 | 约 48 页（38–65 页） |
| 总体积 | 约 2.3 GB（PPT 占大头，单份最大 73 MB） |
| 本机 PDF 解析能力 | **当前不可用**（本地 CLI 未就绪，退出码 127）→ 解析必须由 BB 侧建设，不能假设现成 |
| **来源批次（内部记录，不对外展示）** | **单批**：用户确认为 2025 年省赛优秀作品。目录名含「2026」，且 **56 个文件名里没有任何届次或年份标记** → **只在语料级标注一次 `corpusLabel`**，不逐份核对届次、不逐份核对等级。用户已明确不对外展示这两项，逐份抽取属纯成本 |

### 2.1 选题分布（56 份优秀获奖题目 · 按题名统计，一份可命中多类）

> **读法限定**：下表是**一批语料**的快照。它能说明「这批优秀获奖题目扎堆在哪」，
> **不能**说明「这个方向长期饱和」。对外表述统一为「优秀获奖题目中，某方向有 N 份」。

| 题材 | 份数 | 占比 |
|---|---|---|
| 消费意愿 / 购买 / 付费 | 27 | 48% |
| 广东 / 湾区 / 广州 / 深圳 | 28 | 50% |
| Z 世代 / 青年 / 大学生 | 16 | 28% |
| AI / 智能 / 算法 / 数字 | 15 | 26% |
| 文旅 / 非遗 / IP / 文创 | 14 | 25% |
| 满意度 / 体验 / 忠诚 | 9 | 16% |
| 情绪 / 情感 / 心理 | 8 | 14% |
| 健康 / 养老 / 医疗 | 8 | 14% |

**这张表是整个方案的关键依据**，它说明三件事：

1. **「XX 对 XX 的购买意愿及影响因素」已是绝对主流（48%）**。这类题评审一年要看几十份，没有独特切口几乎无法区分。系统必须能告诉用户这一点。
2. **地域高度本地化（50%）**。语料本身多为本地选题，用户若跨地域复用，题目往往不能直接搬，只有方法论可迁移。
3. **存在真实撞车**。情绪赛道 4 份（丑萌产品、漂亮饭溢价、沉浸式乐园情绪、情价比），其中「丑萌入魂」与「情价比」的问题结构几乎同构。

> **由此得出本方案的核心判断：推荐的价值不在「给新题」，在「告诉你哪条路已堵、堵在哪、还有哪个缝没被占」。**

### 2.2 语料的三类已知脏数据

| 问题 | 实例 | 处理 |
|---|---|---|
| 文件名不是真实题名 | `正文(2)`、`正文+`、`红包雨是否能浇灌用户田最终版本pdf` | 题名必须从 PDF 内页提取，不能用文件名 |
| 同题多文件 | `...反向消费行为调研...报告` + `...附录` | 按题名指纹归并为一个作品 |
| 非调查类作品 | 佛山祖庙武术「研学课程设计方案」、乡村创意文旅「项目报告」 | `作品类型` 字段区分，不能当同类推荐 |

### 2.3 与首页真题的关系：两批数据各管一件事

这里最容易出错的不是技术，是**口径**。站内有两批都叫「真题 / 作品」的数据，它们**不是同一种东西**：

| 维度 | 首页真题 `home-cases.ts` | 推荐知识库（56 份语料） |
|---|---|---|
| 来源批次（内部） | 历年、多届 | **单批** |
| 字段厚度 | 9 个展示字段（题目、届次、组别、领域、等级、摘要、标签、浏览、封面） | 6 必填 + 4 增强 + `好在哪` 的完整选题卡 |
| 用途 | 首页展示、点卡片载入题面 | **仅作 AI 推荐依据**，用户不可浏览 |
| 存储 | 前端静态 TS 快照 | 构建产物 `knowledge.json`（§4.4） |
| **对外展示** | 题名、届次、组别、领域、等级全展示 | **一律只说「优秀获奖题目」**，不展届次、层级、等级 |

**三条不可越界的规则**：

1. **首页真题不进知识库**。它只有展示字段，`desc` 是按题名写的摘要而非从研报抽取，
   拿来做推荐依据会让「依据链」变成不可核查的自我循环。
2. **知识库数据不进首页**。语料作品的题名与结论属于原作内容，摆到首页等于把语料变成对外题库，
   与「不做题库」的决定直接冲突。
3. **两批数据不合并统计**。来源批次不同（历年多届 vs 单批），混在一起算出的拥挤度没有解释力
   ——「消费意愿占 48%」和「某几届碰巧有 3 条同类」是两个不可相加的分母。

**这批语料的定位**：学**结构与打法**的「范式样本」，不是「评奖难度标尺」。
用途是让系统知道"别人怎么组织一个可执行的调查"，不是用来估"这个题能不能拿奖"。
**正因为不做难度推断，才不需要对外标层级和等级**——标了反而会被误读成含金量背书。

## 三、三个失败模式与设计对策

这一节是整个方案的重点。不做对策，功能上线后必然出现这三类问题。

### 失败模式一：生成「看着很好但做不了」的题

模型天然偏爱新颖宏大，典型输出：

- 「全国大学生消费行为调查」——本科生抽不到全国概率样本
- 「疫情前后消费对比」——横截面数据做不了因果
- 「基于大数据的实时画像」——没有数据接口

**对策：把可执行性作为生成阶段的硬闸，不是事后提示。**

生成时强制注入约束上下文：`普通本科生团队 / 3 个月 / 预算 2000 元内 / 单城市可完成 / 需拿到 300 份以上有效样本 / 无付费数据源`。不满足则该候选直接重写，不进入候选列表。

### 失败模式二：生成「伪原创」

把「汉服」换「旗袍」、「广州」换「成都」即交差，本质是抄袭。

**对策：双闸。**

1. **相似度闸**：生成题与源选题卡的题名 + 研究问题做语义相似度，超阈值判不合格。
2. **差异声明闸**：每个候选必须显式写出「我与参考作品 X 的差异是 ___」。写不出具体差异（只写「更聚焦」「更深入」这类空话）即判不合格。

### 失败模式三：把奖项等级当成选题质量信号

这类系统最容易犯的错，是给「获奖等级」一个权重，然后排序被奖项牵着走。三个理由都不支持这么做：

1. **收集成本高、可靠度低**。56 份文件名里没有任何等级标记，只能逐份翻封面页核对；
   抽不到就只能猜，而猜出来的等级比没有等级更糟。
2. **等级不可跨层级比较**。省赛一等奖和国赛一等奖不是一个难度标尺，混算没有意义。
3. **获奖受非选题因素影响大**。学校资源、指导老师、答辩发挥都算在内，等级不是选题质量的干净代理。

**对策：打分函数里不设奖项维度，而不是"设小权重"。**

既然对外不展示等级（§4.2.1），收集它就没有产品价值，只剩成本与编造风险。
所以 `award` / `level` **不进入选题卡**，也不进打分。这一维彻底从链路里移除。

> 这是本轮最省事也最正确的一刀：删掉一个维度，等于同时删掉 56 次人工核对、
> 一整类「抽不到就猜」的造假风险，以及一个会误导排序的弱信号。**得分不再受"这个作品拿了什么奖"影响，
> 只受"这个方向还能不能做"影响**——这才是用户需要的排序依据。

## 四、选题卡字段定义

把每份作品解构为一张结构化卡。**分两档：6 项必填（决定能不能推荐）、4 项增强（决定推荐得多好）。**

### 4.1 必填六项

| # | 字段 | 取值 | 抽取方式 | 备注 |
|---|---|---|---|---|
| 1 | `研究对象` | 人群 + 地域范围 | LLM 抽取 + 人工校验 | 地域单独成字段（见 #6） |
| 2 | `问题类型` | 现状描述 / 影响因素 / 意愿测量 / 满意度评价 / 机制解释 / 效果评估 / 空间布局 / 方案设计 | 规则词表 + LLM 复核 | 决定「题型」而不是「题材」 |
| 3 | `理论框架` | SOR / TAM / UTAUT / TPB / 期望确认 / 感知价值 / 无明确框架 / 其他 | LLM 抽取，需给原文依据 | **市调大赛的核心资产，直接决定第 3 阶段能不能写** |
| 4 | `方法栈` | 抽样方式 / 样本量 / 量表来源 / 分析模型（SEM、回归、聚类、AHP…） | 正则抽数字 + LLM 抽方法名 | 样本量必须抽到具体数字，抽不到标 `unknown` |
| 5 | `数据可得性` | A 自采即可 / B 需机构或企业配合 / C 需政府、平台或付费数据 | 由 #4 推导 + LLM 判定 | **对用户价值最高的一维** |
| 6 | `地域绑定强度` | 无关 / 弱（可换城市） / 强（离开该地域不成立） | 由研究对象地域推导 | 语料 50% 本地化，此维不可省 |

### 4.2 增强四项

| # | 字段 | 取值 | 说明 |
|---|---|---|---|
| 7 | `创新点类型` | 新对象 / 新场景 / 新变量 / 新方法组合 / 新视角 | 用于差异声明闸 |
| 8 | `时效性` | 长期有效 / 当前窗口期 / 已过期 | 「后疫情时代」类已过期，不应推荐 |
| 9 | `结论落点` | 纯描述 / 给出对策建议 / 给出方案设计 | 14 份题名含「路径/策略/方案」，说明这是常见范式 |
| 10 | `题材拥挤度` | 同类作品计数 + 撞车作品列表 | **由语料统计生成，非人工写**，见 §5 |

### 4.2.1 语料级来源标注（不进卡片，不逐份核对）

用户已明确：对外**不写届次、不写层级、不写奖项等级**，统一说「优秀获奖题目」。
所以这三项**不做逐卡抽取**，只在 `knowledge.json` 的 `meta{}` 里记一次：

| 项 | 值 | 来源 | 用途 |
|---|---|---|---|
| `corpusLabel` | `优秀获奖题目` | 构建脚本常量 | **对外统一用词**，依据链、LLM 提示、前端文案都用它 |
| `corpusSource` | `2025 年省赛作品` | 构建脚本常量 | **仅内部追溯**，任何接口不返回、任何界面不显示 |
| `corpusBatch` | `single` | 构建脚本常量 | 单批标记。将来追加语料时改为 `multi`，才允许开启趋势（§5.4） |

**这个决定省掉了什么**：原方案要求 BB 按 PDF 封面逐份核对 56 次届次与等级，估约 2–3 人时，
而且属于"抽不到就只能猜"的高风险工序（文件名里实测没有任何届次标记）。
现在改为语料级记一次常量，**成本归零，同时消灭了一整类编造风险**。

**代价与防线**：卡片上不再有层级/等级，所以「拿这个题能不能获奖」这类推断彻底不可做——
这正是我们要的（§3 失败模式三）。但 `corpusBatch: single` 必须保留，否则将来有人追加语料后
会默认算出"趋势"，那是最容易出错的点。

### 4.3 还要人工写一句话

`好在哪`：由人（不是模型）写一句「这个题为什么能拿奖」。

理由：模型的评语会一律写成「选题新颖、方法规范」这类空话，对用户零信息量。这一句是整张卡的灵魂，可以慢，不能假。

### 4.4 知识库形态：构建产物，不是数据库

既然不做正式题库，选题卡就不该进数据库。建议形态：

```
56 份语料（只读，不进仓库）
   ↓  构建脚本（BB 侧，离线执行一次）
选题卡 JSONL（每行一张卡，便于 diff 与逐条修订）
   ↓  校验 + 人工修订（改文件，不改界面）
knowledge.json            ← 构建产物，随服务部署
   ├─ cards[]             选题卡数组（**不含届次/层级/等级**，只有选题本身的结构）
   ├─ facets{}            领域 / 问题类型 / 理论框架的取值枚举
   ├─ crowding{}          预计算的题材簇统计
   │   ├─ base            统计基数（当前 = 56，**不含首页 12 条**）
   │   ├─ batch           'single'（单批语料，无法算趋势）
   │   ├─ trend           null（batch=single 时恒为 null，前端据此禁用比较级）
   │   └─ clusters{}      簇 → 份数 + 成员 id + 占比
   └─ meta{}
       ├─ corpusLabel     '优秀获奖题目'（**唯一对外用词**）
       ├─ corpusSource    '2025 年省赛作品'（内部追溯，不对外）
       ├─ corpusBatch     'single'
       └─ builtAt / corpusVersion / cardCount / missingFields[]
   ↓  服务启动时载入内存
推荐服务
```

三个关键取舍：

| 项 | 传统题库做法 | 本方案 | 理由 |
|---|---|---|---|
| 存储 | 数据库表 + CRUD | **一个 JSON 文件** | 56 张卡（目标 300 张）全程可驻留内存，文件几十 KB 到几 MB |
| 更新 | 后台录入 | **改源 → 重跑构建 → 重新部署** | 语料一年一更，不需要在线编辑 |
| 校验 | 后台审核流 | **构建产出质检报告 + 人工过文件** | 省掉一整套权限与审批 |

好处是把工作量从「建库 + 后台 + 版本 + 权限 + 审批」压到「一个构建脚本 + 一份 JSON」，
完全符合「不做正式题库」的范围控制，且不影响推荐能力。

**必须接受的两个代价**：

1. **不支持在线纠错。** 发现某张卡抽错，只能改源重建。兜底靠 §4.4.1 的质检报告。
2. **知识库是代码资产，不是内容资产。** 它跟着服务版本走，谁改了语料或改了抽取规则，
   只能靠 git 追溯。因此**构建产物必须进 git，并记录构建参数**（语料清单指纹 + 抽取规则版本），
   否则半年后没人说得清某张卡为什么长这样。

#### 4.4.1 质检报告：不写后台，但要能看见

用户看不到题库，**团队必须能看到**，否则抽取质量无从校验。

建议构建脚本额外输出一份静态 `knowledge.review.html`（或 dev 路由下的预览页），列出：

- 每张卡的字段值 + 抽取置信度 + **命中的原文摘录**（便于逐条核对，不必回去翻 PDF）
- 缺字段清单（`missingFields`）按严重度排序
- 题材簇分布表（即 §5 拥挤度的输入）

定位明确：**这是构建流水线的校验环节，不是用户功能，不投入 UI 打磨。**

## 五、题材拥挤度 —— 本方案的差异化能力

基于 §2.1 的实测分布，系统可以在用户输入方向后立即告知「这条路的路况」。它读的是 §4.4 里
`crowding{}` 那张**预计算统计表**——不查库、不调 LLM、不走数据库。

### 5.1 判定逻辑

```
用户方向 → 词表映射到题材簇（题材词表 + 问题类型）
        → 读 knowledge.json 的 crowding{}（构建时已算好）
        → 分三档回报摘要
```

| 档位 | 判据（基数 = 56 份） | 给用户的说法 |
|---|---|---|
| 红 | 同簇 ≥ 8 份（≈14%），或同问题类型占比 > 40% | 「优秀获奖题目中，这个方向已有 N 份同类，最接近的是《X》。要走这条路，你需要一个能说清的差异化切口，否则评审很难区分。」 |
| 黄 | 同簇 3–7 份 | 「优秀获奖题目中有 N 份同类，但切口各不相同（列出 2–3 个已占切口），还剩 ___ 没被占。」 |
| 绿 | 同簇 ≤ 2 份 | 「这个方向在优秀获奖题目中很少见，注意确认数据可得性和评委认知度。」 |

> 三档文案统一以「**优秀获奖题目中**」开头，不出现届次、层级、等级。
> 这句话由模板拼装（`meta.corpusLabel`），不在各处手写，避免有人顺手补一句「2025 年」。

> **阈值必须随基数归一化，不能硬编码成绝对份数。** 上表的 8 / 3 是按 56 份规模定的；
> 若将来累积到 300 份，同样是「8 份」只占 2.7%，却会被误判成红。构建脚本里应写成
> `red: count/base >= 0.14`，并把 `base` 一起写进 `crowding{}`，前端展示时带上基数。

### 5.2 为什么这一维必须进产品

- 用户真实痛点是「不知道自己的题是不是烂大街」，而这一点语料库能直接回答
- 它把「推荐」从「给你三个选项」升级为「帮你判断方向」，决策价值更高
- 实现成本几乎为零（读一张预计算表 + 一次词表映射），可以先上、先验证
- 在「不做题库」的前提下，它是**唯一能让语料价值直接触达用户**的通道

> 建议排在生成能力之前，作为第一个能上线验证的能力。

### 5.3 不做成「题库筛选」的理由

既然定了不做题库，拥挤度就不能长成「按题材筛出一个列表」的形态，否则等于把题库换个壳露出去。
两者的区别：

| | 题库筛选（不做） | 路况摘要（本方案） |
|---|---|---|
| 用户输入 | 点选题材标签 | 一段自由描述的方向 |
| 系统返回 | 符合条件的作品清单，可翻页 | 一个档位 + 一句判断 + 最多 3 个已占切口 |
| 用户后续动作 | 自己逐条看完再决定 | 直接得到「要不要换方向、往哪个缝走」 |
| 语料暴露程度 | 完整规模与全部条目 | 只暴露与当前方向相关的极少量 |

关键差别：**后者只回答「你这个方向堵不堵」，不提供「还有哪些题可看」。用户拿到的是判断，不是菜单。**

### 5.4 单批语料的表述边界（这一节是本方案的诚实底线）

知识库只有**一批**语料（`meta.corpusBatch = 'single'`），这个事实限定了拥挤度能说什么、不能说什么。
**注意：这条限制来自「只有一批」，不是来自「哪一年」**——所以即使对外不标年份，限制依然成立。

**能说的**：优秀获奖题目中，某方向有几份、切口分别是什么、还剩哪里没被占。
这是一个**可核实的横截面事实**。

**不能说的三句**（都要写进前端文案约束与 LLM 系统提示）：

| 禁忌表述 | 为什么不能说 | 应改为 |
|---|---|---|
| 「这个方向**一直**很堵 / 已经是红海」 | 只有一批语料，推不出长期状态 | 「优秀获奖题目中有 N 份这个方向」 |
| 「今年竞争**更**激烈了」 | 没有可比的上一批，连「今年」都不该出现 | 直接删掉比较级与时间词 |
| 「趋势在上升 / 选题风向正在转向 X」 | 单批无法构成趋势 | 「本批题目中 X 类占 N 份」 |

**为什么不能用首页真题补这个缺口**：`home-cases.ts` 虽跨多届，但同时满足
「仅 12 条 + 9 个展示字段 + 摘要非抽取所得」三点。用它当分母不仅补不上批次差异，
还会污染统计——12 条里 3 条同领域就能让占比跳到 25%，而这是抽样噪音不是市场信号。
**用户已确认两批不合并，这个判断在统计上是站得住的。**

**语料累积后的演进路径**：

| 语料批次 | `crowding{}` 能提供 | 对外可用的表述 |
|---|---|---|
| **1 批（现状）** | 份数 + 已占/未占切口 | 「优秀获奖题目中有 N 份……」 |
| 2 批 | 份数 + 两批增减方向 | 「相比上一批增加 / 减少 N 份」 |
| ≥ 3 批 | 份数 + 趋势 + 稳定饱和判定 | 「连续 N 批都在增长」 |

因此 `crowding{}` 要预留 `batch` 与 `trend`：现在 `batch='single'`、`trend=null`，
前端与 LLM 侧按「`trend === null` 就不许出现比较级」硬拦。将来追加语料只需重跑构建，
不用改接口契约。**改 `batch` 是唯一能开启趋势判断的开关**，因此它成为一个需要评审的动作。

## 六、推荐打分

### 6.1 打分函数

```
score = 0.30 × 领域匹配
      + 0.25 × 问题类型匹配
      + 0.25 × 数据可得性适配（A=1, B=0.6, C=0.2）
      + 0.20 × 新颖度（由拥挤度反向归一）
      − 地域绑定惩罚（用户跨省时为 0，强绑定则为 −0.15）
```

权重取舍说明：

- **四项刚好归一（0.30+0.25+0.25+0.20 = 1.00）**，没有奖项项，因此不需要再归一化一次。
  删掉奖项维度后权重天然凑满，这也侧面说明它本来就是多余的。
- **数据可得性 0.25 与领域匹配同档**。学生最怕的不是题不够新，是拿不到数据。
- **新颖度直接由拥挤度反推**，不再单独造一个「新颖性」指标，避免两个指标互相打架。
- **没有奖项维度**。理由见 §3 失败模式三：成本高、不可比、不是干净的选题质量代理。

### 6.2 多样性重排

前三名不能全落在同一问题类型。采用 MMR（最大边际相关）：每选出一个候选后，后续候选与已选集合的题材相似度按 0.5 折减。

目的是防止「推荐三个都是消费意愿类」，那等于没推荐。

### 6.3 可解释性要求（不做题库之后，这一节变得更关键）

用户不能自己浏览题库判断，只能看到 3 个候选。理由一旦空洞，「凭什么信你」就无从回答。
所以每个候选必须能回答两件事：

**一、为什么推荐它** —— 理由必须引用**具体字段**，不是空话：

- ✓「与你的方向同属数字科技，且数据可得性 A 级（自采 400 份问卷即可）」
- ✗「这个题很符合你的兴趣」

**二、它站在什么依据上** —— 必须能展开「依据」，且只呈现与该候选相关的极少量：

```
依据 · 优秀获奖题目中的 2 份同方向作品
├《Z世代"心"市场——AI情感陪伴产品需求、使用动机与意愿研究》
│  有效样本 ______ 份 · 方法 ______ · 数据可得性 A
│  已占切口：需求 + 使用动机 + 意愿（三因素并列）
└《AI虚拟陪伴：情感体验与用户留存机制研究》
   有效样本 ______ 份 · 方法 ______ · 数据可得性 A
   已占切口：情感体验 → 留存（纵向机制）

你的题避开了「三因素并列」，改走「留存的行为数据」，这两份都没做。
```

> **示例里的空格是有意留的。** 样本量、方法栈必须来自真实抽取结果，抽取没跑之前不能填。
> 本方案全文不臆造任何作品的样本量、系数或结论——**依据链一旦掺假，整条推荐链路就失去信用**。

**依据里要标什么、不标什么**：

| 标 | 不标 |
|---|---|
| 「优秀获奖题目」这个统一前缀 | 届次、年份（「2025 年」「第 N 届」） |
| 题名（公开信息，用户可自行查证） | 层级（省赛 / 国赛） |
| 样本量、方法、数据可得性、已占切口 | 奖项等级（省一 / 国二） |

理由：用户要判断的是「这个切口被占到哪里、我还能不能换角度」，这三项对判断没有贡献；
标上去反而会把注意力引向"含金量"，而那些信息既不完整也不可比。

**这不是「暴露题库」**：用户看到的是 2 条证据，不是可浏览的 56 条清单。
缺了这一层，推荐就退化成一个不可核查的黑箱——这是取消题库前台后必须补的一课。

若确实不宜显示题名，可退化为聚合表述（「参考 2 份同赛道获奖作品，平均样本量 471 份，
主流方法 SEM」），但**优先显示题名**：获奖作品题名本身是公开信息，且用户能自行查证。

## 七、生成环节的硬规则

不写代码，但规则要定死，否则 prompt 会在后续迭代中不断退化成「随便写写」。

### 7.1 输入

检索阶段选出的 2–3 张选题卡（完整字段）+ 用户方向与约束 + 拥挤度报告。

**检索方式：不上向量库。** 56–300 张卡的量级，用「结构化字段过滤 + 关键词映射到题材簇」就够：

- 先按领域 / 问题类型过滤到 10–20 张
- 再按 §6.1 打分排序取前 3
- 全程可解释，每一步都能说出为什么进候选、为什么被排除

在这个规模下引入向量库，收益极小，却多一个部署依赖和一层不可解释的相似度。
等语料过千再考虑——知识库本来就是构建产物，换检索方式不改数据形态。

**不给模型留「自由发挥」的空间**：必须基于指定卡片做变体，不允许凭空造题。

### 7.2 输出（每个候选必须七项齐全）

| 项 | 要求 |
|---|---|
| 题目 | 符合市调大赛命名习惯（主标题 + 破折号 + 副标题） |
| 研究对象与场景 | 具体到人群与城市范围 |
| 问题类型 | 从固定枚举里选，不许自造 |
| 理论框架 + 方法栈 | 明确到量表来源与主分析模型 |
| 数据方案 | 从哪采、多少人、多久、多少钱 |
| **与源卡的差异** | 必须具体，写空话即判不合格 |
| **风险提示** | 一句「这个题最可能死在哪」 |

### 7.3 强制项：风险提示

**每个候选必须附一条否定意见。** 这是抑制模型输出「看起来很美的空题」最有效的手段。

示例：「样本需要覆盖高净值人群，学生难以接触，且涉及收入提问，拒答率可能超过 30%。」

### 7.4 兜底

- 三重校验不过（相似度、差异声明、可执行性）时，**宁可少给候选，也不降低标准**。返回 1 个合格候选好过返回 3 个凑数的。
- 若语料中确无匹配选题卡，明确回报「现有语料里没有接近的方向」，不要硬生成。

## 八、接口契约建议（交 P 与 BB 评审）

### 8.1 前端需要的两个接口

**A. 方向探查（不依赖 LLM，建议先上）**

只读 `knowledge.json` 的 `crowding{}`，无推理成本。

```
POST /api/research/topic-crowding
req:  { direction: string, problemType?: string, region?: string }
res:  {
        level: 'red' | 'yellow' | 'green',
        count: number,
        /* —— 以下是「不许说趋势」的硬约束所需，缺一项前端无法组织合法文案 —— */
        base: number,                    // 统计基数，当前恒为 56（不含首页 12 条）
        corpusLabel: string,             // 恒为 '优秀获奖题目'，前端原样拼进文案
        batch: 'single' | 'multi',       // 当前恒为 'single'
        trend: null | { delta: number }, // batch='single' 时恒为 null，前端禁用比较级
        similar: [{ caseId, title, occupiedAngle }],   // 不返回届次/层级/等级
        occupiedAngles: string[],        // 已被占的切口
        gaps: string[]                   // 尚未被占的切口
      }
```

> `base`、`corpusLabel`、`batch` 是**必返字段**，不是装饰。前端所有档位文案都拼成
> 「`corpusLabel` 中有 `count` 份……」；`trend === null` 时模板层直接剔除比较级句式。
> 这样 §5.4 的话术约束由接口与模板共同保证，而不是靠写文档提醒后人。
> `corpusLabel` 由后端给而不是前端硬编码，是为了将来若改口径只需改一处。

**B. 候选推荐（需要 LLM）**

```
POST /api/research/topic-recommend
req:  { direction, discipline?, region?, group?, methodLevel?, topK: 3 }
res:  {
        candidates: [{
          title, object, problemType, framework, method,
          dataPlan: { source, sampleSize, months, budget },
          diffFromSources: string,
          risk: string,
          evidence: [{                          // 依据链，见 §6.3
            caseId, title,
            sampleSize,                         // 抽不到就是 null，**不许模型补**
            method, dataGrade, occupiedAngle
            // 不返回 edition / level / award —— 见 §6.3「标什么、不标什么」
          }],
          score, reasons: string[]
        }],
        crowding: { ...同 A },
        note?: string                           // 语料无匹配时的说明
      }
```

两个接口都**只返回与当前方向相关的极少量条目**，不提供列表、不提供分页、不提供按题材遍历。
这是「不做题库」在接口层的落实。

### 8.2 现状缺口

| 缺口 | 现状 | 需要谁补 | 何时需要 |
|---|---|---|---|
| 无解析流水线 | 本机 PDF 解析不可用（本地 CLI 退出码 127） | BB | P0 就要 |
| 无知识库 | 无 `knowledge.json` | BB 写构建脚本产出 | P0 就要 |
| 无拥挤度统计表 | 无 | BB 构建时预计算，随知识库一并产出 | 第一个接口就要 |
| 无 LLM 调用层 | `src/api/` 下 20 个模块，**没有任何 LLM 调用** | 需先定后端承载方 | P2 才需要 |

对照原本的四个缺口，**「无选题卡存储」这条随「不做正式题库」一起消失**——
不需要 BA 建表、建后台、建审批流、建权限。

仍要提醒一条硬约束：`home-cases.ts` 那 12 条是前端静态快照、只有 9 个展示字段，
**不能用于推荐**；它和知识库是两回事，不要混用（也无需合并）。

## 九、分工建议

不做正式题库后，这条链路从四方收缩为**三方**，BA 不再参与建库。

| 环节 | 责任方 | 交付物 |
|---|---|---|
| 语料归集、去重、题名校正 | BB | 56 份作品的规范化清单（题名、报告、PPT、作品类型） |
| PDF / PPT 解析与结构化抽取 | BB | 选题卡 JSONL + 置信度 + 质检报告 |
| 选题卡人工校验与「好在哪」撰写 | 内容侧（F 或课程侧可承担） | 校验后的选题卡终版 |
| 知识库构建与产物入库 | BB | `knowledge.json` + 构建参数记录（进 git） |
| 拥挤度统计与推荐服务 | BB | 接口 A / B 实现 |
| 前端推荐交互与依据展示 | F | 第 2 阶段入口组件 |
| 接口契约与公共状态接入 | P | 类型定义 + 接入层 |

**风险提示**：缩到三方仍不可缺一。F 单方只在前端拼 prompt 调模型，产出的是一次性演示、无法复用。

**新增一条纪律**：知识库从「内容资产」变成「代码资产」之后，**构建产物与构建参数必须进 git**。
否则「某张卡为什么长这样」半年后无法追溯——这是取消后台审核后唯一留下的审计手段。

## 十、分期落地

**与前一版的关键差异**：原 P0 是「选题灵感库」（前台可浏览 56 条选题卡），
随「不做正式题库」作废。重构后 P0 变成**内部可见、用户不可见**的知识库建设。

| 期 | 内容 | 交付物 | 用户可见 |
|---|---|---|---|

**P0 的验收方式也随之改变**：不看页面好看不好看，看**字段抽对率**与**构建可重复性**（§11）。

### 10.0 为什么 P0 仍然是那 10 条样卡

即使不做题库，这 10 条也必须单独先做——它是整条链路的探针：

- 字段够不够用（做完才知道「地域绑定强度」「理论框架」是否真能抽出来）
- 抽取可靠不可靠（同一份报告抽两次，结果会不会不一致）
- 人工校验到底多费时（决定全量 56 条要不要做、要不要缩到 30 条）

三个问题不实验就答不了；而**做 10 条的成本，远低于做满 56 条之后才发现方向错了**。

### 10.1 样卡建议选型

从 56 份里挑，覆盖不同问题类型与难度，避免全是消费意愿类：

| 建议纳入 | 理由 |
|---|---|
| AI 情感陪伴（2 份同赛道） | 直接体现「撞车」与「同题不同切口」，是拥挤度功能的最佳教材 |
| 公共图书馆数字化服务「体验鸿沟」 | 三角互证、非消费类，方法栈复杂，测抽取上限 |
| 中老年人智能健康监测设备 | 涉及弱势群体，数据可得性 B 级，测「可执行性」判定 |
| 佛山祖庙武术研学课程设计 | 非调查类，测「作品类型」字段是否必要 |

| # | 项 | 判据 |

## 十三、一句话总结

**这个功能的成败不取决于模型，取决于选题卡做得实不实。**

不做正式题库这个决定是对的：它省掉了一整套表结构、后台管理、权限与审批，而推荐能力一点没少。
但**有三样东西不能一起省**——

1. **依据链**（§6.3）。用户看不到题库，就只剩 2–3 条证据来判断该不该信你。这是取消题库前台后必须付的补偿。
2. **质检报告**（§4.4.1）。团队看不到抽取结果，质量就无从校验，构建出来的是一堆没人核对过的 JSON。
3. **口径守线**（§5.4、§6.3）。对外统一说「**优秀获奖题目**」，不标届次、不标层级、不标等级；
   同时也**不许说「一直」「更」「趋势」**。这两条是一体两面：**不标时间，不等于可以下长期判断。**
   省掉后半条，「一批语料」就会被读成「这个方向的长期规律」，那是这类产品最容易犯的错。

**首页真题与推荐知识库是两套东西，不要因为都叫「真题」就凑到一起**：一批是历年多届的展示数据，
一批是单批推荐依据；字段厚度、用途都不同，合并统计得出的拥挤度没有解释力。
这条内部纪律虽然不对外展示，但**它决定了对外那句「优秀获奖题目中」到底成不成立**。

第一笔投入放在那 10 条样卡上：便宜，能立刻回答三个关键问题，而且无论后面走不走 AI，
这 10 张卡都是整条链路里唯一的真实资产。
